## 1. Project Overview

**Purpose.** Aura ("💫" is used as a logo emoji throughout the UI, see `templates/base.html`)
is a self-hosted web application for running **human evaluation campaigns** of machine-generated
text — primarily Machine Translation (MT), but the code generalizes to summarization,
simplification, dialogue/response generation, question answering, factuality/hallucination
checking, and fully custom tasks (see `models.TASK_TYPES`). Two special-focus languages/scripts
constants (`SCRIPT_OPTIONS`, `LANGUAGE_SCRIPTS` in `utils/constants.py`) show a strong focus on
**Northeast Indian languages** (Assamese, Manipuri/Meitei, Bodo, Khasi, Mizo, Naga languages,
Santali, etc.) and their scripts (Bengali–Assamese, Meitei Mayek, Devanagari, Ol Chiki, Wancho,
Tai, Tibetan).

**Main features:**
- Admin-created **campaigns**, each with its own segments (source/target pairs), evaluation
  mode, rating scale, and instructions.
- Five evaluation modes per campaign (`Campaign.eval_mode`): `likert`, `pairwise`,
  `preference_selection`, `span_only`, `post_edit` (see §6/§25).
- Per-campaign **qualification tests** that annotators must pass before rating "real" segments
  (`QualificationTest` / `QualificationAttempt` — a fully separate, isolated grading pipeline).
- Optional **AI guideline assistant** embedded in the rating UI (Anthropic/OpenAI/Gemini/
  OpenAI-compatible), advisory-only, with an optional randomized A/B eligibility experiment.
- Rich **statistics/results engine** (`results.py`): inter-annotator agreement (Krippendorff's
  alpha, Cohen's/Fleiss' kappa), Pearson/Spearman correlation, Elo ratings for preference
  ranking, span-level F1, edit-distance for post-editing, per-system breakdowns, disagreement/
  "contested segment" detection, difficulty-tier breakdowns.
- **Exports**: master CSV, results ZIP (CSV + PNG charts + JSON + standalone HTML report),
  emailed to the campaign owner automatically when a campaign is closed.
- Admin and Annotator **self-service accounts** with email+OTP verification, password reset,
  and (for admins) invite-code/domain-restricted signup.
- **Campaign groups**: bundle related campaigns (e.g. easy/medium/hard variants) for combined
  results/export.
- Demo/seed data loader for populating the dashboard with synthetic campaigns/annotators/
  ratings (`seed_data.py`) — **[INFERRED note]**: the `demo_data/` directory it reads from
  (`campaigns.json` + `segments/*.csv`) is **not included** in this ZIP.

**Type of project:** Server-rendered Flask web application (Jinja2 templates + vanilla JS
progressive enhancement — no SPA framework, no Node/npm build step is referenced anywhere).

**Target users:** Two roles —
1. **Admins** (research leads / project managers) who create and configure campaigns, review
   results, manage annotators.
2. **Annotators** (human raters) who sign up per-campaign, take a qualification test, and rate
   segments.

**Tech stack:**
- Backend: **Python 3** + **Flask** (see `create_app.py`, `app.py`)
- ORM: **Flask-SQLAlchemy** (`extensions.py`)
- Migrations: **Flask-Migrate** / **Alembic** (`migrations/`)
- Database: **PostgreSQL** in production (`psycopg2` driver string in `config.py`); a SQLite
  file (`data/app.db`) is used as a legacy/local source for the one-off migration script
  (`scripts/migrate.py`).
- Auth/crypto: **bcrypt** (password + OTP hashing), **cryptography.Fernet** (AI-provider API
  key encryption at rest, `llm.py`)
- Numeric/stats: **numpy** (`results.py`)
- Charting: **matplotlib** (`Agg` backend, PNGs base64-embedded into reports)
- Email: hand-rolled HTTP clients for **Resend** and **SendGrid** APIs, plus classic **SMTP**
  fallback (`mailer.py`) — no third-party SDK, just `urllib.request`/`smtplib`.
- Frontend: server-rendered Jinja2 HTML + hand-written vanilla JavaScript
  (`static/rate.js`, `static/campaign_form.js`, `static/results.js`,
  `static/password_validation.js`) + hand-written CSS (`static/style.css`,
  `static/qualification/qualification.css`) + a vendored `chart.umd.min.js`
  (Chart.js UMD build) in `static/vendor/`.
- Env/config: **python-dotenv** (`.env` loading in `config.py` / `app_setup.py`)

**Build tools:** None detected — no `webpack`/`vite`/`package.json`. Static assets are served
directly by Flask's static file handler; JS/CSS are plain files, no bundling/minification step
in the repo. **[INFERRED]** Deployment is likely a plain WSGI process (`app.py` exposes
`app = create_app()` for a WSGI server, e.g. gunicorn) — no `Procfile`/`Dockerfile` was present

**Runtime:** CPython. `f-string`/`match`-free modern syntax throughout; compiled `.pyc` files

instance, though the source doesn't hard-require any particular 3.x version).

**Package managers:** `pip` (**[INFERRED]** from `pip install --break-system-packages` style

**Framework versions:** Not pinned anywhere in the ZIP — **[INFERRED: unknown]**. Third-party

## 3. Entry Points

**Server startup (`app.py`):**
```python
from create_app import create_app
app = create_app()
if __name__ == "__main__":
    app.run()
```
`app.py` is both the WSGI entry point (`app` module-level variable, importable by
gunicorn/uwsgi/etc.) and the dev-server entry point (`python app.py`).

**Bootstrap flow (`create_app.py` → `create_app()`):**
1. `Flask(__name__)` instantiated.
2. `app.config.from_object(Config)` — loads `config.Config` (reads env vars, calls
   `load_dotenv()` at import time).
3. `init_extensions(app)` (`extensions.py`) — binds SQLAlchemy `db` and Flask-Migrate
   `migrate` to the app.
4. `register_components(app)` (`app_setup.py`) — sets `SECRET_KEY` (via
   `utils.security.load_secret_key()`), registers a `@app.context_processor` that injects
   `current_annotator` and `page_role` into every template, registers the `flask test-email`
   CLI command, and registers the `/healthz` route.
5. `register_blueprints(app)` (`routes/__init__.py`) — registers 8 blueprints (see §6).
6. `register_cli(app)` (`commands/cli.py`) — registers `flask seed-demo` /
   `flask unload-demo`.
7. Returns the fully configured `app`.

**Database schema creation:** via Alembic/Flask-Migrate (`flask db upgrade`), not
`db.create_all()` — the single migration `f2345a55758b_initial_schema.py` builds every table.

**Client-side "startup":** No SPA bootstrap. Each Jinja2 template that needs interactivity
inlines a `<script>` block setting `window.CAMPAIGN`, `window.SEGMENTS`, etc. as globals, then
loads the relevant static `.js` file which reads those globals inside an IIFE
(`(function(){ "use strict"; ... })()`) — see `static/rate.js` lines 1-40 for the pattern.

## 4. Architecture

**Style: Layered, Blueprint-per-domain Flask monolith** (not MVC in the classic sense — there
are no "Controller" classes; Flask view functions serve that role directly).

```
routes/ (view functions, Blueprint per role×domain)
   │  reads request, calls services/ + models, renders templates or JSON
   ▼
services/ (business logic: auth, qualification lifecycle, AI prompt construction)
   │  pure(-ish) functions operating on model instances
   ▼
models.py (SQLAlchemy ORM: Campaign, Annotator, Rating, QualificationTest, ...)
   │
   ▼
extensions.db → PostgreSQL
```

Supporting horizontal layers used by all the above:
- `utils/` — stateless parsing/validation helpers (form parsing, file ingest, constants) used
  directly by `routes/admin/*` (form collection is NOT delegated to `services/`; it lives
  inline in the route modules as large `_collect_*_form` helper functions).
- `results.py` / `exporter.py` — a separate "reporting" layer, called only from
  `routes/admin/results.py` and `routes/admin/campaigns.py` (on campaign close).
- `llm.py` / `mailer.py` — outbound integration layers (third-party HTTP APIs), imported
  directly by routes and services with no adapter/interface abstraction.

**Why this classification:** Business rules that are genuinely reusable across roles (password
policy, OTP, session helpers, qualification grading) are pulled into `services/`. However, a
large amount of **form-collection/validation logic for campaigns lives directly inside
`routes/admin/campaigns.py`** (`_collect_campaign_form`, ~330 lines) rather than a service —
this is a **pragmatic layering choice, not strict Clean Architecture**; the codebase favors
one flat, well-commented file per concern over deep abstraction layers.

`models.py` is a single file (not a `models/` package) containing every table — a deliberate
simplicity trade-off documented nowhere explicitly but evident from the code: at 1470 lines it
is the largest "domain" file after `routes/admin/campaigns.py` and `results.py`.

## 5. Complete Request / Data Flow

### Example: Annotator submits a rating (likert mode)

```
Browser (rate.html + rate.js)
   │  fetch POST /campaign/<id>/api/submit  {segment_id, scores, spans, comments, ...}
   ▼
Flask routing (routes/annotator/rating.py :: api_submit)
   │  @require_annotator  (services/auth_service.py — checks session['annotator_id'])
   ▼
api_submit(campaign_id):
   1. c = Campaign.query.get_or_404(campaign_id)
   2. Reject if c.is_closed (403 JSON)
   3. ann = current_annotator()
   4. can_annotate(ann, c)  (services/qualification.py) → 403 if not yet qualified
   5. Validate payload against c.mode-specific rules (score bounds, preference id, span bounds...)
   6. Upsert `Rating` row (unique on campaign_id+annotator_id+segment_id)
   7. db.session.commit()
   ▼
Response: {"ok": true}
```

### Example: Admin views campaign results

```
Browser  GET /admin/campaign/<id>/results
   ▼
routes/admin/results.py :: admin_campaign_results
   │  @require_admin
   1. c = owned_campaign_or_404(campaign_id)     (services/auth_service.py — ownership check)
   2. res, frozen = _campaign_results(c)
        - if c.is_closed and c.results_snapshot_json: use frozen JSON snapshot
        - else: crit = get_criteria_for(c); ratings = Rating.query.filter_by(campaign_id=c.id).all()
                 res = results.compute_results(c, ratings, crit)   [results.py — mode-dispatch stats]
   3. charts = results.build_charts(res)          [matplotlib → base64 PNG data URIs]
   4. render_template("admin_campaign_results.html", campaign=c, results=res, charts=charts, ...)
```

### Example: Campaign close → snapshot + email export

```
POST /admin/campaign/<id>/close (routes/admin/campaigns.py :: admin_campaign_close)
   1. c.closed_at = utcnow(); db.commit()
   2. results.compute_results(...) → c.results_snapshot_json (frozen forever)
   3. exporter.build_results_zip(c, completed_ratings, criteria, res, charts, report_html)
   4. mailer.send_email(c.owner_email, subject, body, attachments=[zip])
```

### Middleware / cross-cutting concerns (no true Flask `before_request` middleware is used;
instead, per-view decorators and a context processor handle these):

- **`@require_admin`** / **`@require_annotator`** (`services/auth_service.py`): session-based
  gatekeeping; returns 401 JSON for API-like requests (`/api/` in path, XHR header, or
  `Accept: application/json`), else redirects to the relevant login page with a flash message.
- **`owned_campaign_or_404` / `owned_group_or_404` / `admin_owns`**: per-admin data isolation —
  a campaign/group with a non-empty `owner_email` is only visible to the admin whose email
  matches (case-insensitive); legacy rows with empty `owner_email` are visible to everyone.
- **`@app.context_processor` (`inject_globals`, in `app_setup.py`)**: runs on every render,
  injects `current_annotator` and `page_role` (derived from the endpoint name prefix:
  `admin_*` → `"admin"`, `annotator_*`/`rate_view`/`api_submit`/`api_config` → `"annotator"`,
  else `"public"`) so `base.html` can render the right header without every view passing it.

"error": "..."}` with a 400/403 status for API endpoints.

## 7. Services

### `services/auth_service.py`
- **Responsibility:** All authentication/authorization/session logic for both Admin and
  Annotator roles, using a **role-parameterized design** (`_ROLE_MODELS = {"admin": Admin,
  "annotator": Annotator}`) so password-reset/OTP/update-password code is written once and
  shared.
- **Business logic:** env-var "super admin" bypass (`ADMIN_EMAIL`/`ADMIN_PASSWORD`) alongside
  self-registered `Admin` rows; invite-code and email-domain gating for admin signup; ownership
  checks (`admin_owns`, `owned_campaign_or_404`, `visible_campaigns_query`) that scope every
  admin to campaigns they created (or legacy unowned ones).
- **Dependencies:** `models` (Admin, Annotator, Campaign), `extensions.db`, `mailer`
  (`send_password_reset_otp`, `send_otp`).
- **Used by:** every route module (`routes/admin/*`, `routes/annotator/*`) for the
  `@require_admin`/`@require_annotator` decorators and ownership helpers.
- **Important algorithms:** none numeric; `generate_otp()` uses `secrets.randbelow` for a
  6-digit code; `password_problems()` enforces length + character-class rules.
- **Dead/commented code:** lines 237–265 contain a commented-out earlier version of
  `start_annotator_signup`/`verify_annotator_signup_otp` left in place above the live
  implementations further down the same file (see §29).

### `services/qualification.py`
- **Responsibility:** Full lifecycle of a qualification attempt: eligibility check
  (`can_annotate`), starting/resuming attempts (`start_attempt`, `get_open_attempt`), retry
  policy (`retry_status` — max attempts + cooldown window), submission (`submit_attempt`),
  and **grading** (`grade_attempt` — exact-match grading per eval mode) plus updating the
  annotator's global `qualification_status`.
- **Business logic:** Grading is **exact-match only** for every mode (scores dict equality,
  preference id equality, spans dict equality, whitespace-trimmed edited-text equality) — no
  partial credit.
- **Dependencies:** `models` (QualificationAttempt, QualificationResponse, QualificationSegment,
  QualificationTest, Annotator), `extensions.db`.
- **Used by:** `routes/annotator/qualification.py` (all views), `routes/annotator/rating.py`
  (`can_annotate` gate before serving/accepting ratings).

### `services/ai_assistant.py`
- **Responsibility:** Builds the **system prompt** and **user prompt** sent to the configured
  LLM for the in-rating "guideline assistant" — grounds the assistant in the campaign's actual
  instructions/criteria/scale/preferences and the segments currently visible to the annotator,
  and explicitly instructs it never to reveal or influence the rating decision itself.
- **Business logic:** `_interface_help()` generates mode-specific UI explanation text (how to
  use circles/buttons/radio/stars/slider, pairwise vs. selection vs. span vs. post-edit
  workflows). `task_label()` maps a campaign's `task_type` to its human name via
  `models.task_defaults`.
- **Dependencies:** `models` only (no Flask/DB access — pure prompt-construction functions).
- **Used by:** `routes/annotator/rating.py :: api_assist` (calls `llm.call_llm` with these
  prompts).
- **External APIs:** none directly — delegates the actual HTTP call to `llm.py`.

## 8. Controllers (Flask View Functions)

Flask has no separate "Controller" layer; view functions in `routes/**` fill that role. Key
ones beyond the routing table in §6:

- **`admin_campaign_new` / `admin_campaign_edit`** (`routes/admin/campaigns.py`): the most
  complex controllers in the app — collect and cross-validate ~40 form fields plus an uploaded/
  pasted segments file (and, for `_new`, an *embedded* qualification-test sub-form with a field
  prefix of `qual_`, extracted via `extract_prefixed_subform`). Both delegate parsing to
  `_collect_campaign_form` and render via `_render_new_campaign_form`/`_render_edit_campaign_form`
  on validation failure so the user's input isn't lost.
- **`admin_campaign_close`**: orchestrates snapshotting results, rendering a full offline HTML
  report, zipping everything (`exporter.build_results_zip`), and emailing it — wrapped in nested
  `try/except` blocks so a failure in reporting never blocks the campaign from being marked
  closed.
- **`rate_view`** (`routes/annotator/rating.py`): the densest read-path controller — computes
  served segments (difficulty/expertise filtering + per-annotator shuffle), existing ratings,
  scale legend, pairwise/selection candidate normalization, and AI-assist eligibility per
  segment, all before rendering `rate.html`.
- **Response structure:** HTML views render Jinja2 templates; JSON API views
  (`/api/*`, `*.json`) return `{"ok": bool, ...}` envelopes with appropriate 4xx codes on
  failure (400 validation, 401 auth via `_wants_json()`, 403 forbidden/closed, 502 upstream LLM
  error).

## 9. Database

- **Type:** PostgreSQL (production; via `psycopg2` connection string built in `config.py`).
  A SQLite file was used historically/locally (see `scripts/migrate.py`, which migrates
  `data/app.db` → Postgres).
- **ORM:** SQLAlchemy via Flask-SQLAlchemy (`db = SQLAlchemy()` in `extensions.py`).
- **Migrations:** Flask-Migrate/Alembic. Only **one** migration file exists
  (`migrations/versions/f2345a55758b_initial_schema.py`), meaning the schema has been
  **squashed into a single "initial" migration** — this is either a fresh project or history
  was deliberately collapsed. **[INFERRED]**
- **Primary keys:** every table uses a 32-char hex string (`uuid.uuid4().hex` via
  `models._uuid()`) as its `id`, not an autoincrementing integer.
- **Indexes:** explicit `index=True` on foreign keys and lookup fields (`Annotator.email`,
  `Admin.email`, `Rating.campaign_id/annotator_id/segment_id`, `CampaignGroup` FK on
  `Campaign.group_id`, qualification FKs).
- **Foreign keys / relationships:**
  - `Campaign.group_id` → `CampaignGroup.id` (nullable; `passive_deletes=True` — deleting a
    group detaches campaigns rather than cascading).
  - `Rating.campaign_id` → `Campaign.id`, `Rating.annotator_id` → `Annotator.id`; unique
    constraint on `(campaign_id, annotator_id, segment_id)` — one rating per annotator per
    segment per campaign, upserted in place.
  - `Campaign.qualification_test` — one-to-one via `QualificationTest.campaign_id`
    (`unique=True`), `cascade="all, delete-orphan"` — deleting a campaign deletes its
    qualification test, which cascades to delete its segments/attempts (and those cascade to
    responses).
  - `QualificationAttempt` → `QualificationTest`, `Annotator`; `QualificationResponse` →
    `QualificationAttempt`, `QualificationSegment`.
  - `CampaignAnnotator` — join-table-like model (not a pure association table; has its own
    `id` + extra columns) linking one `Campaign` to one `Annotator`, unique on the pair, storing
    admin evaluation (`quality_score`, `has_star`) and annotator-submitted "Form B" background
    fields (location, parents' language, time spent abroad, exposure).
  - `AnnotatorCampaignPref` — per-(annotator, campaign) UI preference (segments-per-page),
    unique on the pair.
  - `AssistantLog` — one row per AI-assistant Q&A interaction, FK to `Campaign` and (nullable)
    `Annotator`.
- **How data moves:** `Campaign.segments_json` / `criteria_json` / `preferences_json` /
  `scale_labels_json` / `results_snapshot_json` are **all JSON-encoded TEXT columns**, not
  normalized tables — segments, criteria, and rating-preference options are schemaless blobs
  parsed on read via `@property` accessors (`Campaign.segments`, `.criteria`, `.preferences`).
  This is a deliberate design allowing flexible per-campaign segment shapes without schema
  migrations per task type.

## 10. Models

(Full field lists are in `models.py`; only non-obvious fields/relationships are called out.)

Global account (works across all campaigns). Fields: `name`, `email` (unique), `email_verified`,
`password_hash` (bcrypt), OTP fields (`otp_hash`, `otp_expires_at`, `otp_attempts`),

### `CampaignGroup` (`campaign_groups`)
`name`, `description`, `owner_email`. `campaigns` relationship is `lazy="dynamic"`,

Key field groups: task/labels (`task_type`, `input_label`, `output_label`), languages/scripts
(`source_language`, `target_language`, `script`, `source_script`, `target_script`), difficulty
config (`difficulty_method`, `difficulty_easy_max/hard_min`, `served_difficulties`,
`expertise_matching`), layout (`rating_position`, `span_position`), segments/criteria/
preferences (JSON text columns, see §9), scale config (`scale_type/points/min/max/design/
labels_json`), AI-assistant config (`ai_enabled`, `ai_ab_enabled/fraction`, `ai_provider/model/
base_url`, `ai_api_key_enc` — Fernet-encrypted), incentives (`incentive_co_authorship/money/

(deterministic per-(campaign,annotator,segment) hash-based A/B assignment).

One annotator's judgment of one segment in one campaign. `scores_json`, `spans_json`,

One AI Q&A turn: `campaign_id`, `annotator_id`, `segment_id`, `role`, `provider`, `model`,

### `CampaignAnnotator` (`campaign_annotators`)
Per-(campaign, annotator) admin evaluation + "Form B" demographic/exposure fields (see §9).
Unique on `(campaign_id, annotator_id)`.

### `AnnotatorCampaignPref` (`annotator_campaign_prefs`)
Per-(annotator, campaign) UI preference, currently just `segments_per_page`. Unique pair.

### `QualificationTest` (`qualification_tests`)
One-to-one with `Campaign` (`campaign_id` unique). `title`, `language`, `description`,

One annotator's attempt: `started_at`, `submitted_at` (null while in progress),

(sequential attempt number). Relationship: `responses` (cascade delete-orphan).

### `QualificationResponse` (`qualification_responses`)
One answer: `response_json`, `is_correct`, `score`, `time_spent_seconds`.

## 11. Authentication

**Two entirely separate, parallel auth systems** sharing helper code via
`services/auth_service.py`'s role-parameterized functions:

**Admin:**
- **Bootstrap admin**: `MT_EVAL_ADMIN_EMAIL`/`MT_EVAL_ADMIN_PASSWORD` env vars (defaults
  `admin@example.com` / `change-me`) — always valid, no DB row, checked first in
  `admin_login()`.
- **Self-registered admins**: `Admin` model, `is_verified` gate. Signup requires (if configured)
  an invite code (`MT_EVAL_ADMIN_INVITE_CODES`, comma-separated, checked via
  `hmac.compare_digest`) and/or an allowed email domain (`MT_EVAL_ADMIN_EMAIL_DOMAINS`).
  Can be globally disabled via `MT_EVAL_ADMIN_SIGNUP_ENABLED=0`.
- **Sessions**: Flask server-side cookie session; `login_admin()` calls `session.clear()` then
  sets `is_admin=True` + `admin_email`. No JWT/OAuth anywhere in the codebase.
- **Password reset**: email+6-digit-OTP flow (`generate_otp()` → `secrets.randbelow`), OTP
  bcrypt-hashed and time-limited (`otp_expires_at`, default 15 min via `set_otp`), max attempts
  tracked but **not actually enforced as a lockout anywhere observed** (`otp_attempts` field
  exists but is never incremented/checked — **[INFERRED gap]**, see §29).

**Annotator:**
- Global account, but **login/registration is scoped by `campaign_id`** in the URL (routes
  live under `/annotator/campaign/<campaign_id>/...` and `/campaign/<campaign_id>/...`) even
  though the underlying `Annotator` row is shared across all campaigns.
- Signup requires: name, valid email, password meeting `password_problems()` policy (≥8 chars,
  upper+lower+digit+symbol), consent checkbox, native language, location, dialect, age group,
  and (conditionally) expertise level and/or source/target fluency depending on the campaign's
  `difficulty_method`/`is_cross_lingual`.
- Email verification via OTP required before login (`email_verified` flag).
- **Sessions**: `login_annotator()` sets `session["annotator_id"]` + `session["last_campaign_id"]`
  (used to redirect back into the right campaign after actions like logout).
- **No refresh tokens** anywhere — this is classic server-side session auth
  (`PERMANENT_SESSION_LIFETIME = 30 days`, `SESSION_REFRESH_EACH_REQUEST = True` in
  `config.py`).

**Middleware:** `@require_admin` / `@require_annotator` decorators (see §5) are the sole
enforcement point — there is no global `before_request` auth check; each protected view opts
in explicitly.

**Roles:** exactly two — `admin` and `annotator`. No "super-admin"/"reviewer"/etc. sub-roles.
Per-campaign **ownership** (`owner_email`) is the closest thing to fine-grained authorization
(see §12).

## 12. Authorization

- **Roles:** `admin`, `annotator` (session-flag based: `session["is_admin"]` /
  `session["annotator_id"]`).
- **Permissions:** binary per role — any admin can create campaigns; any annotator can attempt
  any campaign's qualification test (gated only by qualification pass/fail, not by any
  allow-list).
- **Access control / data isolation:** the only fine-grained control is **campaign/group
  ownership** — `admin_owns(obj)` compares the current admin's email to `obj.owner_email`
  (case-insensitive); **empty `owner_email` = visible to all admins** (back-compat for
  pre-ownership rows). `owned_campaign_or_404`/`owned_group_or_404` 404 (not 403) on a
  non-owned resource, deliberately hiding existence from other admins. `visible_campaigns_query()`
  applies the same filter at the query level for list views.
- **No row-level annotator restriction** beyond qualification status — any qualified annotator
  can rate any served segment of a campaign they're logged into.

## 13. Middleware

Flask-level middleware is minimal; most cross-cutting behavior is decorator- or
context-processor-based (no `@app.before_request` hooks were found in the code read).

| "Middleware" | Type | Purpose | Applied to |
|---|---|---|---|
| `require_admin` | route decorator | Session check, redirect/401 | All `/admin/*` protected views |
| `require_annotator` | route decorator | Session check, redirect/401, smart campaign-aware redirect | All annotator-only views |
| `inject_globals` | `@app.context_processor` | Injects `current_annotator`, `page_role` into every template render | Global (all templates) |
| `load_dotenv()` | module-level, run at import of `config.py` and `app_setup.py` | Loads `.env` into `os.environ` | Runs once at process start |

**Execution order** (per request touching a protected admin view):
`load_dotenv (import time)` → Flask session cookie parsing (built-in) → view decorator
(`require_admin`) → view body → `inject_globals` context processor (during template render).

## 15. State Management

No client-side state library (no Redux/Zustand/Context/Vuex/Pinia/React Query/SWR — there is
no React/Vue at all). State is managed via:

## 16. API Layer

There is no dedicated "API client" module or fetch wrapper shared across JS files — each
`static/*.js` file calls the browser's native `fetch()` directly against the JSON endpoints in
§6 (e.g. `rate.js` posts to `window.SUBMIT_URL`/`window.CONFIG_URL`, both server-injected
globals pointing at the Flask routes). No axios, no interceptors, no client-side caching layer,
no retry logic observed. Server responses follow a consistent `{"ok": bool, ...}` JSON envelope
(see §8).

`llm.py` implements the app's only true "API client" pattern — a provider-agnostic dispatcher
(`call_llm`) over `urllib.request` (no `requests` library dependency) supporting Anthropic,
Gemini, and OpenAI-compatible chat-completions shapes, with a monkeypatchable
`_http_post_json` for testability.

## 17. Utilities

### `utils/constants.py`
Static reference data driving both server validation and template rendering:
`CRITERIA_DEFAULTS` (Adequacy/Fluency/Meaning preservation), `CRITERION_COLOR_POOL`,
`EVAL_MODES` (the 5 modes with descriptions), `SCALE_TYPES`/`SCALE_DESIGNS`, `SCRIPT_OPTIONS`

### `utils/forms.py`
Pure form-parsing helpers used exclusively by `routes/admin/campaigns.py` and
`routes/admin/qualification.py`: `parse_scale_from_form` (validates Likert points 2-11 /
continuous bounds, falls back to `Campaign.default_likert_labels()` when no custom labels
given), `parse_criteria_from_form` (parallel `crit_name[]`/`crit_desc[]` arrays → slugified-id
criteria list, tracks missing descriptions), `parse_preferences_from_form` (pairwise option
labels → slugified-id list), `extract_prefixed_subform`/`extract_prefixed_subfiles` (pulls a
`qual_`-prefixed sub-form out of the combined campaign-creation `<form>` so the embedded
qualification-test fields don't collide with the campaign's own same-named fields).

### `utils/ingest.py`
Segment-file parser supporting **JSON, JSONL/NDJSON, CSV, TSV**, and content-sniffed `.txt`/
pasted text (`parse_segments_upload`). Normalizes known columns (`id, source, target, reference,
system, domain, target_a, target_b, candidates`), coerces a `candidates` cell (JSON array or
`|`/`;`/tab-delimited string) into a list, strips a UTF-8 BOM, sniffs CSV vs TSV delimiter from
the header line. Preserves unknown columns verbatim as extra segment metadata.

### `utils/security.py`
`load_secret_key()` — returns `MT_EVAL_SECRET_KEY` env var if set, else reads/creates a
persisted key at `DATA_DIR/secret_key` (`secrets.token_hex(32)`) so `SECRET_KEY` (and thus
session cookies) survive restarts across multiple worker processes without requiring the env
var in dev.

## 22. Error Handling

- **No custom exception hierarchy** for domain errors — the one custom exception is
  `llm.LLMError`, raised for any provider HTTP/parsing failure and caught specifically in
  `routes/annotator/rating.py :: api_assist` (returned as a 502 JSON error) and in
  `llm.test_config` (returned as `(False, message)`).
- **Logging:** Python stdlib `logging`, configured once in `app_setup.py`
  (`logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(name)s:
  %(message)s")`). Module-level loggers: `logging.getLogger(__name__)` in `app_setup.py` and
  `routes/admin/campaigns.py`; `logging.getLogger("aura.mailer")` in `mailer.py`.
- **Error swallowing pattern:** several `except Exception:` blocks with `logger.exception(...)`
  followed by a user-facing flash message rather than a crash — notably in
  `admin_campaign_close` (results snapshot + email export failures never block the close
  action itself) and `admin_seed_demo`/`admin_unload_demo`.
- **No monitoring/APM/Sentry integration** was found in the codebase.
- **Retry mechanisms:** none for the LLM/email HTTP calls (single attempt, error surfaced to
  caller) — **[INFERRED absence]**, no retry/backoff logic was found in `llm.py` or `mailer.py`.
- **User-facing errors:** Flask `flash()` messages (categories: `"error"`/`"danger"`/`"info"`/
  `"success"`) for HTML views; `{"ok": false, "error": "..."}` JSON for API views.
- **404 handling:** Flask's default `get_or_404()`/`abort(404)` pattern throughout — notably
  used deliberately for authorization failures (`owned_campaign_or_404`) to avoid leaking
  resource existence to unauthorized admins.

## 26. Hidden Logic

- **No background job queue, scheduler, or cron** was found anywhere in the codebase (no
  Celery/RQ/APScheduler import, no cron config file). All "async-feeling" work (results ZIP
  build + email on campaign close) happens **synchronously inline within the request** that
  closes the campaign (`admin_campaign_close`), wrapped in try/except so failures don't block
  the redirect.
- **No event emitters / pub-sub** — all communication between layers is direct function calls.
- **No WebSocket usage** — the "live update" behavior in the rating page (`rate.js` polling
  `/api/config`) and the results dashboard (`/results-version`, `/results-fragment`) is
  implemented via **client-side polling**, not push/WebSockets.
- **Deterministic pseudo-randomness used as hidden logic:**
  - `Campaign.ai_ab_eligible()` — SHA1 hash of `(campaign_id, annotator_id, segment_id)` mod
    100, compared to `ai_ab_fraction`, to assign AI-assistant availability per-pair without
    storing a separate assignment table.
  - `Campaign._shuffle_for_annotator()` — SHA1-seeded `random.Random` per `(campaign_id,
    annotator_id)` to produce a stable-but-randomized segment presentation order without
    storing per-annotator ordering explicitly.
  - `results._elo_ratings()` — Elo rating computation over pairwise/selection comparisons for
    system ranking (`k=32, base=1000.0, epochs=30, seed=42` — fixed seed for reproducibility).
- **Frozen result snapshots:** `Campaign.results_snapshot_json`, written once at close time,
  silently changes the behavior of every results-reading route thereafter (`_campaign_results`
  helper in `routes/admin/results.py` checks `is_closed and results_snapshot_json` first) — this
  is easy to miss when reading only the "live" computation path.

## 30. AI Quick Reference

**Project:** *Aura* — a Flask-based, human-evaluation platform for MT/LLM-generated text
(translation, summarization, simplification, dialogue, QA, factuality, or fully custom tasks),
with a strong practical focus on Northeast Indian languages/scripts. Two roles: **Admin**
(creates/configures/monitors campaigns) and **Annotator** (qualifies via a per-campaign test,
then rates segments).

**Architecture:** Layered Flask monolith. `routes/` (Blueprints, view functions = controllers)
→ `services/` (auth, qualification lifecycle, AI-prompt building) → `models.py` (single-file
SQLAlchemy ORM) → PostgreSQL. Supporting: `utils/` (stateless parsing/validation), `results.py`
(stats engine), `exporter.py` (CSV/ZIP), `llm.py` (multi-provider LLM client), `mailer.py`
(Resend/SendGrid/SMTP). Server-rendered Jinja2 + vanilla JS (no SPA framework, no build step).

**Main folders:** `routes/admin/*` (campaign CRUD, results, auth), `routes/annotator/*`
(campaign login/signup, rating, qualification, dashboard), `services/` (business logic),
`utils/` (helpers), `templates/` (Jinja2 HTML), `static/` (CSS/JS, `rate.js` is the biggest and
most important client file), `migrations/` (single squashed Alembic migration).

**Important services:**
- `services/auth_service.py` — session auth, role-parameterized password/OTP helpers, campaign
  ownership isolation (`admin_owns`, `owned_campaign_or_404`).
- `services/qualification.py` — attempt lifecycle + exact-match grading + retry policy.
- `services/ai_assistant.py` — prompt construction for the optional AI guideline assistant
  (never reveals ratings; grounded in the campaign's own instructions).

**Important routes:** `/admin/campaign/new` (creates campaign + embedded qualification test in
one transaction), `/campaign/<id>/rate` + `/api/submit` (the core annotation loop),
`/campaign/<id>/qualification*` (gate before rating), `/admin/campaign/<id>/results*`
(dashboards/exports), `/admin/campaign/<id>/close` (freezes results, emails a ZIP).

**Key models:** `Campaign` (segments/criteria/preferences stored as JSON text columns —
schemaless by design), `Rating` (one per annotator×segment×campaign, unique-constrained,
upserted), `QualificationTest`/`Segment`/`Attempt`/`Response` (fully parallel, isolated data
model from production `Campaign`/`Rating`), `Annotator`/`Admin` (bcrypt + OTP auth),
`CampaignAnnotator` (per-pair admin evaluation + demographic "Form B"), `CampaignGroup`.

**Authentication:** Session-cookie based (no JWT/OAuth). Env-var bootstrap admin +
self-registered `Admin`/`Annotator` rows, both gated by email OTP verification. Two totally
separate auth flows sharing generic helpers via a `role` parameter in `auth_service.py`.

**Data flow (canonical):** Browser → Flask route (`@require_admin`/`@require_annotator`) →
`services/*` for business rules → `models.py` ORM operations → `extensions.db` → PostgreSQL →
JSON or Jinja2 HTML response.

**Key conventions AI assistants should know before editing:**
1. **Segments/criteria/preferences are JSON blobs**, not normalized rows — read/write via the
   `Campaign.segments` / `.criteria` / `.preferences` `@property` accessors, never assume a
   `Segment` table exists.
2. **Campaign segments are immutable after creation**; only the qualification test's segments
   can be replaced later.
3. **Five eval modes** (`likert`, `pairwise`, `preference_selection`, `span_only`, `post_edit`)
   fan out through nearly every layer (`rating_is_complete`, `_csv_header`, `compute_results`,
   `grade_attempt`, the rating template/JS) — when adding a new mode, all of these must be
   updated in parallel; grep for `eval_mode ==` / `mode ==` / `campaign.mode` to find every
   branch point.
4. **Ownership isolation is by email string comparison** (`owner_email`), not a foreign key to
   an `Admin.id` — legacy rows with empty `owner_email` are visible to *every* admin.
5. **Qualification is per-campaign**, never global — passing one campaign's test never
   qualifies an annotator for another.
6. **`Campaign.config_fingerprint()`** must be updated (add the new field to its `parts` list)
   whenever a new annotator-visible config field is added, or the live-refresh polling on the
   rating page won't detect the change.
7. Import cycles are avoided via **function-local imports**, not module reorganization — follow
   the existing pattern when adding new cross-module references between `models.py` and
   `utils/`/`results.py`.
